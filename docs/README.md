# ドキュメントの方針

## 残すもの（docs/ 直下）

永続化するのは次の3つだけ。

| 種類 | 置き場所 | 中身 |
|---|---|---|
| 要件 | [requirements.md](requirements.md) | 作品の目的、守る方針、満たすべきこと |
| 基本仕様 | [spec.md](spec.md) | 技術構成、データの大きな流れ、ブランチとデプロイ。変わりにくい骨格だけ |
| なぜそう決めたか | [decisions/](decisions/) | 決めたこと、退けた案、根拠 |

## 詳細設計（docs/_wip/）

- 実装を始めるときに `docs/_wip/<テーマ>.md` に書く。テーブル定義、APIの形、画面の細部などがここに入る
- 実装が終わったら次のように片付ける
  - 要件・基本仕様・判断の理由にあたるものは docs/ に移す
  - それ以外は削除する（その内容はソースが持っている）
- 詳細設計はソースを正とする。docs/ の記述とソースが食い違ったら、ソースを信じる。docs/ を直すのは、要件・基本仕様・判断の理由が変わったときだけ

## 「なぜそう決めたか」の書き方

`decisions/NNNN-短い名前.md` に、一つの判断を一つのファイルに書く。番号は連番にする。

```markdown
# NNNN 題名

- 日付: YYYY-MM-DD
- 状態: 採用 / 置き換え済み（→ NNNN）
- 決めた人: 人間 / fable-advisor に相談（相談したエージェント名）

## 決めたこと
## 理由
## 退けた案とその理由
## 根拠にしたもの（ドキュメントのURL、出し比べの記録、計測値など）
## 見直す条件（どうなったら考え直すか）
```

判断が変わったときは古いファイルを書き換えない。新しいファイルを作り、古いファイルの状態を「置き換え済み」にする。
