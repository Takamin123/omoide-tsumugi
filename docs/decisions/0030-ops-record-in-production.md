# 0030 運営の記録の画面を本番で開く。読み取り専用の別の鍵と、同意を得た家族の許可の一覧で守る

- 日付: 2026-11-03
- 状態: 採用
- 決めた人: fable-advisor に相談（backend-developer）。運営が同意を得て本番の記録を見ること、家族を作る鍵とは別の鍵で守ることは人間（0027）

0025 の画面の中身（返すもの・返さないもの、言葉）と 0026 の見せ方はそのまま。ここでは鍵と、本番での扱いだけを置き換える。

## 決めたこと
- `/api/ops/*`（record と写真の画像）は、全環境（手元・プレビュー・本番）で新しい秘密 `OPS_RECORD_TOKEN`（`Authorization: Bearer`）で守る。家族を作る鍵（CREATE_FAMILY_TOKEN）でも、家族の合言葉の cookie でも開かない。確かめは routes/auth.ts の一か所（requireInvite）で行い、routes/ops.ts でも重ねて確かめる（0025 のまま）
- 鍵の設定が 32 文字より短いとき、または CREATE_FAMILY_TOKEN と同じ値のときは「設定なし」とみなし、誰も開けない。そのときはログに `{ event: "ops_key_misconfigured", reason }` と種類だけを残す（値は残さない）
- 見られる家族は、環境ではなく家族の種類で分ける
  - デモの家族（is_demo）は、鍵だけで開く
  - デモでない家族は、鍵に加えて、秘密 `OPS_RECORD_FAMILIES`（カンマ区切りの家族 ID）に載っているときだけ開く。載っていなければ、存在しないものとして 404（ない家族と同じ本文）
  - record と写真の画像の両方に掛ける。写真の入り口も、写真を読む前に家族を読んで確かめる
  - ops から APP_ENV の分岐を無くす。`devToolsOpen` は /check だけのものに戻す
- 画面 `/ops/record` は本番のビルドにも入れる（常に lazy で、chunk は家族の画面と分ける）。`__CHECK_PAGE__` は /check だけを指し、/check は本番のビルドに入れないまま（0014）
- 鍵は画面のタブの sessionStorage のまま（0025）。localStorage にも URL にも置かない
- 見たことの記録は、今ある record の取得のログ（家族 ID と件数）のまま。写真の取得は残さない。親への同意の言葉に「いつ見たかは残る」とは書かない（Workers のログはそこまで保たれない）
- 鍵の作り方と取り替え: 32 文字以上のランダムな値（例: `openssl rand -base64 32`）を人間が作り、`wrangler secret put`（手元は .dev.vars）で登録する。漏れたら新しい値で登録し直す（上書きで古い値は無効）
- 人間の段取り（0027 に足すもの）
  - 本番で親の家族を作った後、その家族 ID を `OPS_RECORD_FAMILIES` に登録する。登録しないと、鍵が合っていても 404
  - 家族を消すときは、`OPS_RECORD_FAMILIES` からもその ID を外す（実際の家族の識別子を秘密の値に残さない）

## 理由
- requirements「プライバシー」の例外（運営が見る）は、0027 で人間が「親の同意を得て」と決めた。同意の範囲（親の一家族）と、技術的に開く範囲を一致させる。鍵が漏れても、読めるのはデモの家族と同意を得た家族だけ
- requirements「デモ用のデータは実際の家族と分ける」: is_demo がその線。環境ではなく家族の種類で分けると規則が一つになり、プレビューで本番と同じ道（デモでない家族と許可の一覧）を確かめられる。0025 が is_demo の分岐を退けたのは「本番でデモの家族だけ見る」文脈で、今回は実際の家族を見るのが目的
- implementation-policy 4「既定で閉じる」「ほかの家族のものは、存在しないものとして 404」
- 0027「家族を作る鍵とは別の鍵」を、設定の誤り（同じ値の使い回し）からも守る。黙って閉じると、運営が「鍵の打ち間違い」と「設定が弾かれた」を見分けられず、試しの直前に詰まる
- 実際の家族の ID は公開のリポジトリに入れない（0006 の Cloudflare の ID とは性質が違う）
- 本番の画面は、鍵の入力欄と「運営と開発だけが見る画面」の一行しか出さない。家族の一覧も写真もないので、0014 が /check を退けた理由（画像解析ツールの顔をした、半分動かないページ）には当たらない

## 退けた案とその理由
- 本番だけ別の鍵（手元・プレビューは CREATE_FAMILY_TOKEN のまま）: 環境で鍵の意味が変わり、プレビューで本番の守りを確かめられない。節約できるのは登録の一回だけ
- 家族を絞らない: 同意の範囲と開く範囲がずれる形を最初から作ることになる
- 許可の一覧を wrangler.jsonc の vars に置く: 実際の家族の識別子が公開のリポジトリに入る
- D1 の families に同意の列を持つ: 正しい形だが、マイグレーションと同意の記録の設計が要り、今日は重い。二家族目で移す
- 手元・プレビューだけ絞らない: APP_ENV の分岐が ops に残り、プレビューで許可の一覧の道を試せない。手元で触るのはデモの家族だけ（implementation-policy 4）
- 設定の誤りを黙って 401 にする: 運営が原因を見分けられない
- 鍵をメモリだけに持つ: 0026 で URL に載せた再読み込みと戻る・進むのたびに鍵の再入力になる。localStorage と URL は 0025 のまま不可
- 画面の URL を推測しにくくする: 守りは鍵。見せかけで守らない
- 写真の取得もログに残す: record を開かずに写真だけを取る使い方は画面になく、ログが増えるだけ

## 見直す条件
- 同意を得た実際の家族が二つ目になったとき → families に同意の記録を持ち、`OPS_RECORD_FAMILIES` をやめる
- 鍵の設定の誤りのログが本番で出たとき → 鍵を作り直す（値は人間が打つ）
- 記録の画面に書き込み（「見た」の印など）を足したくなったとき → 読み取りだけの前提が崩れるので、改めて相談する
- 親が「消して」と言ったとき → 0027 の消す手順に加えて、`OPS_RECORD_FAMILIES` から ID を外す
