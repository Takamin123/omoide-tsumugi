# 0029 問いかけの読み上げの本番の仕組み（毎朝の処理で作り、R2 に置く）

- 日付: 2026-11-03
- 状態: 採用
- 決めた人: fable-advisor に相談（backend-developer）

## 決めたこと
- 毎朝の処理は、全員の入り口（Claude の入り口と固定の入り口）を作り終えてから、二周目で、今日の kind=claude の入り口に音声を作る。音声の締め切りは処理の始まりから 9 分（`MORNING_SPEECH_DEADLINE_MS`）。締め切りを過ぎる呼び出しや再試行はしない（一回の時間切れは「60 秒」と「残り」の短い方）。受け取れた音声は、締め切りに関係なく保存まで行う
- 冪等: 音声がある入り口には作らない。失敗して音声がない入り口は、同じ日の再実行（デモのボタンなど）で作ってよい。ただし、**一度家族に見せた入り口（shown_at あり）には、音声も後から足さない**（「一度見せた入り口は差し替えない」の読み。祖父母が一度見た画面に後からボタンが現れないようにする）。この条件はデータベースの更新の条件で止め、入れられなかったら保存した音声は消す
- entrances に `question_audio_key`、`question_audio_model`、`question_audio_voice` を足す（ADD COLUMN だけ）。**CHECK は足さない**。SQLite では CHECK を足すと表の作り直しになり、実際の家族のデータが入る本番の D1 では避けたい。kind='claude' にだけ入れる条件は、リポジトリの更新の条件（`setQuestionAudio`）で守る
- R2 の鍵: `families/<familyId>/speech/<entranceId>-<uuid>.mp3`。0027 の消す手順（`families/<id>/`）に入る。uuid は、同時に二つ走ったときに相手の音声を消さないため
- 家族向け: `GET /api/entrances/today` の入り口に `questionAudioUrl`（`/api/entrances/<id>/question-audio`）か null。音声は合言葉の確認の後に返し、`Cache-Control: private, no-store`。ほかの家族の入り口は 404。null のとき（固定の入り口、作れなかった日、キーがない）は、画面にボタンも「AI の声で読みます」も出さない
- 声の設定（gpt-4o-mini-tts、marin、速さ 1.0、指示文、mp3）は `src/server/core/question-speech.ts` の一か所の定数 `QUESTION_SPEECH`。実機で聞き比べるまでの仮の値（0019、0027。今は /check の初期値と同じ値）。/check の初期値とは結びつけない（0014。/check は試す場所で、変えても本番は動かない）。行に model と voice を残すので、後で定数を変えても出所は残る
- 読み上げの口は `Speaker`（ports）。開発用の `SpeechProbe` とは別に、応答を検証する（audio/*、mp3 の頭、大きさの上限）。時間切れ・再試行は implementation-policy 2 のとおり。ログは ID・モデル・声・長さ（バイト数）・所要時間・失敗の種類だけで、文は出さない。OpenAI のキーがなければ作らない

## 理由
- implementation-policy「失敗したとき」は入り口を出すことを最優先にしている。音声は入り口に足すもので、0019 も「作るのが失敗しても入り口は出す」としている
- implementation-policy「毎朝の処理」（足りない分だけ作る、冪等、10 分以内）、requirements「プライバシー」、0019「採るときの形」、0027

## 退けた案とその理由
- 一人ずつ、入り口を作った直後に音声を作る: 音声の最悪 2 分半が後の人の Claude の予算（7 分）を食い、音声のために固定の入り口が増える。主従が逆
- 一度試したら、失敗でもその日は作らない: 一時的な失敗（429 など）を一日の失敗に固定する。試した印の列も要る
- CHECK で kind='claude' を縛る: SQLite では表の作り直しになる
- 一度見せた入り口にも後から音声を足す: 文は変わらないが、見た画面に後からボタンが現れる

- 2027-01-06 の前にモデルの後継を決めるとき（0019）
- 実機で聞き比べて声・速さ・指示を変えるとき（定数を変える）
